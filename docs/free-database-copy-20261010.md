# 기존 데이터의 무료 Supabase 프로젝트 복사

새 Supabase 프로젝트는 Free 요금제를 사용합니다. 기존 Neon 데이터베이스와 프로젝트는 삭제하거나 초기화하지 않습니다. 새 프로젝트의 데이터베이스 연결 정보는 서버와 GitHub Actions에만 전달하며 웹 화면의 공개 API 키로 사용하지 않습니다.

## 연결과 실행 순서

1. [Supabase 대시보드](https://supabase.com/dashboard)에서 새 무료 프로젝트의 **Connect → Session pooler** 연결 주소를 준비합니다. GitHub의 IPv4 환경에서 연결할 수 있는 포트 `5432` 주소를 사용합니다.
2. [저장소 Actions secrets](https://github.com/seokjeongeum/cheongyak-calendar/settings/secrets/actions)에 새 주소를 `SUPABASE_DATABASE_URL`로 저장합니다. 기존 `DATABASE_URL`은 원본 읽기에 사용하므로 복사가 완료되기 전에는 변경하지 않습니다. 주소나 비밀번호를 이 문서·커밋·실행 로그에 넣지 않습니다.
3. 기존 수집을 멈춘 상태에서 **Copy existing application database** 수동 워크플로를 `work` 브랜치로 한 번 실행합니다. 수집 예약을 다시 켜지 않아도 실행할 수 있습니다. 새 DB에는 아직 앱을 연결하지 않습니다. 앱 데이터가 이미 있는 대상은 덮어쓰지 않고 실행을 중단합니다.
4. 결과가 `complete`이고 모든 `copied_rows`와 `verified_rows`가 같을 때 서버와 수집의 연결을 새 DB로 바꿉니다. 공식 자료·가격·경쟁률·이력·API 연결 상태를 확인한 뒤 정기 수집을 다시 사용합니다.

## 복사 범위와 실패 처리

명령 `python -m app.migrate_database`는 `SOURCE_DATABASE_URL`과 `TARGET_DATABASE_URL`을 사용합니다. 수동 워크플로는 각각 기존 `DATABASE_URL`과 새 `SUPABASE_DATABASE_URL` secret을 연결합니다. 복사는 명시한 한 번의 수동 실행에만 적용하며, 수집의 동시 실행 그룹을 공유합니다. 정기 수집은 복사가 검증되고 연결을 전환할 때까지 중지합니다.

원본은 PostgreSQL의 **REPEATABLE READ / READ ONLY** 한 트랜잭션에서 읽습니다. 원본 스키마를 업그레이드하거나 데이터를 수정하지 않습니다. 실제 원본 열을 확인하고 새 nullable 열은 대상에만 생성합니다. 알 수 없는 원본 테이블·열을 발견하면 조용히 버리는 대신 복사를 중단합니다.

앱 모델의 모든 테이블을 복사합니다. 공고 UUID와 사업 식별자, 원본 JSON과 문서 해시, 가격, 경쟁률과 확인 상태, 공고·경쟁률 이력, API 키와 관리자 해시, 기관별 수집 기록, 중단·재시도 체크포인트를 그대로 유지합니다. 정정·중복 공고의 자기 참조는 공고를 모두 넣은 뒤 복원합니다. 숫자 ID의 다음 값은 보존된 최댓값 뒤에서 시작합니다.

대상의 테이블 생성·복사·관계 복원·검증은 한 트랜잭션입니다. 원본의 한도 제한 또는 연결 실패, 복사 오류나 행 수 불일치는 대상 변경을 롤백합니다. 기존 대상 데이터는 삭제하지 않습니다. PostgreSQL 앱 테이블에는 RLS를 적용해 공개 Data API 역할의 기본 접근을 차단합니다. 앱은 기존 서버 DB 연결을 사용합니다.

로그에는 완료 상태, 테이블별 행 수 또는 고정된 실패 코드만 출력합니다. DB 주소·비밀번호·API 키·원본 레코드와 SQL 오류 내용은 출력하지 않습니다. 앱 데이터 복사 후 새 DB 연결로 전환하는 작업은 이 명령에 포함하지 않습니다.

## 로컬 검증

SQLite와 연결 오류 검증 16개가 통과했습니다. 모든 앱 테이블, 큰 한국어 원본 JSON, API 키·관리자 해시, 가격·경쟁률·이력, 양방향 공고 참조, 체크포인트와 다음 ID를 대조했습니다. 기존 대상 보존, 원본 연결 거부 시 대상 미접속, 도중 실패의 전체 롤백, 원본 쓰기 차단, 새 nullable 열이 없는 원본 보존, 미지원 스키마 거부와 로그 비밀값 미출력도 확인했습니다. 새 DB의 연결을 먼저 확인해 접속 실패 시 원본 조회를 시작하지 않습니다. IPv6 연결·호스트·pooler 사용자·비밀번호·시간 초과 오류는 비밀값 없이 고정된 코드로 구분합니다.

2026-10-11 올바른 Session pooler 연결을 저장한 뒤 [수동 이전 실행](https://github.com/seokjeongeum/cheongyak-calendar/actions/runs/38091453699)이 성공했습니다. 원본은 변경하지 않았습니다. 공고 540건, 접수 일정 1,465행, 가격 1,165행, 경쟁률 1,795행, 공고 이력 1,255행, 경쟁률 이력 146행, 경쟁률 상태 152행, 문서 체크포인트 541행, 연결 설정 4행, 수집 실행 1행, 기관 상태 7행을 복사했습니다. 모든 `copied_rows`와 `verified_rows`가 일치하며 대상 DB의 별도 행 수 조회도 일치합니다. 기존 공공데이터·Gemini 연결 상태와 관리자 해시 존재 여부도 비밀값을 조회하지 않고 확인했습니다.

실제 PostgreSQL 17에서 JSONB 서버 병합의 원본·순서 보존과 앱 테이블 11개의 RLS, 전송량 캐시 열을 확인했습니다. Supabase의 기본 RLS 설정 함수는 공개 역할에서 실행하지 못하도록 제한했습니다. 보안 점검에는 의도적으로 정책을 만들지 않은 서버 전용 테이블의 정보 항목만 남았습니다. Render와 GitHub의 연결 전환은 별도로 확인해야 합니다.
